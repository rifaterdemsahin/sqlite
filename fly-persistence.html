Making SQLite Persistent Across Restarts & Deploys on Fly.io

By default, container root filesystems (/app) are ephemeral: redeploying or restarting a container wipes any changes made inside /app. To make SQLite 100% durable on Fly.io while preserving its local POSIX file-locking requirement, we attach a dedicated Fly NVMe Volume (`sqlite_data`) mounted at /data.

1. Visual Architecture: Ephemeral Container RootFS vs. Persistent Fly Volume (`/data`)

Why Fly Volumes work safely with SQLite whereas network file shares (NFS/SMB) corrupt it: Fly Volumes are slices of a local NVMe drive physically attached to the same host server where your Firecracker Micro-VM runs.

2. How It Is Configured in This Project (`fly.toml` + `Dockerfile` + `sandbox.py`)

Three small pieces connect your Python application to the persistent `/data` volume on Fly.io:

A. `fly.toml` — Mount `sqlite_data` to `/data`

app = "sqlite-ai-sandbox"
primary_region = "lhr"

[env]
  PORT = "8080"
  HOST = "0.0.0.0"
  SANDBOX_DATA_DIR = "/data"

[[mounts]]
  source = "sqlite_data"
  destination = "/data"
  initial_size = "1gb"

B. `sandbox.py` — Read `SANDBOX_DATA_DIR`

# Reads /data on Fly.io or ./sandbox_data locally
SANDBOX_DIR = os.environ.get(
    "SANDBOX_DATA_DIR",
    os.path.join(BASE_DIR, "sandbox_data")
)
DB_PATH = os.path.join(
    SANDBOX_DIR,
    "ai_workflow_sandbox.db"
)

# On first boot, if /data/ai_workflow_sandbox.db
# does not exist yet, init_sandbox_db() creates it
# in WAL mode and seeds initial records.

3. How Fly.io SQLite Persistence Works Under the Hood (and Scaling Patterns)

Understanding the storage architecture, why single-writer rules apply, and how to back up or replicate your persistent SQLite file:

Mechanism How It Works on Fly.io Command / Best Practice
1. Local NVMe Block Volume (`[[mounts]]`) Fly Volumes allocate an ext4 filesystem on a physical NVMe drive on the host running your Firecracker VM. Because it is a real local block device (not NFS/SMB), SQLite's `fcntl()` POSIX locks and shared-memory `-shm` mmap files work at native speed without corruption. fly volumes list
fly ssh console -C "ls -lh /data"
2. Auto-Stop & Auto-Start Safety When `auto_stop_machines = "stop"` suspends your VM during idle periods, the `/data` volume remains attached to that machine. When an HTTP request wakes the machine up (~300ms), `/data/ai_workflow_sandbox.db` is immediately present with all your CRUD edits intact. Test in SQL & CRUD Studio: insert a row, redeploy, and query it again!
3. Daily Automatic Snapshots Fly.io automatically takes daily block-level snapshots of every volume and retains them for 5 days (configurable up to 60 days). fly volumes snapshots list <vol-id>
4. Instant Single-File SFTP Backup Because the whole SQLite database is one ordinary file, you can download a consistent hot backup from your Fly machine to your Mac at any time. fly sftp get /data/ai_workflow_sandbox.db ./fly_backup.db
5. Continuous S3/Azure Blob Replication (Litestream / LiteFS) For zero-RPO disaster recovery or multi-region read replicas, run Litestream (streams WAL frames continuously to Azure Blob Storage / S3) or LiteFS (FUSE filesystem that replicates SQLite transactions across Fly nodes). litestream replicate /data/ai_workflow_sandbox.db s3://my-bucket/db
